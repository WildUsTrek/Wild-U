Wildu Game Guard Patcher

Mini-app standalone per proteggere gli HTML dei giochi Wild-U dal click diretto esterno. Incolli il link reale del gioco, la pagina prova a scaricare automaticamente l’index originale, poi genera un index.html protetto che avvia il gioco solo dopo il ticket del launcher.

Offline Nessun backend Patcha solo HTML

Regola d’oro: il launcher crea il ticket, ma il blocco reale del click diretto deve stare nell’index del gioco. Questo tool aiuta a inserire il bootstrap guard senza far impazzire i tecnici.

Input

Esempio: https://wildustrek.github.io/Wild-U/giochi/sfida-dei-sassi/index.html. Il tool deduce da solo target, path guard e cartella.

Fallback manuale

Come trovare l’index originale se l’auto-fetch fallisce
  1. Apri il link reale del gioco in browser.
  2. Tasto destro → Visualizza sorgente pagina, oppure aggiungi view-source: davanti all’URL.
  3. Copia tutto il sorgente HTML e incollalo nel box qui sopra.
  4. Oppure scarica la cartella dal repository GitHub e carica il file con il selettore.

Controlli automatici del tool
  • Calcola path relativo verso /Wild-U/shared/wildu-secure-game-guard.js.
  • Rileva script classici <script src="...">.
  • Evita di patchare due volte se trova già il guard.
  • Avvisa se trova script inline, module script, async/defer o nessuno script.
  • Non modifica CSS, markup, testi, pulsanti o logica del gioco.

Manuale sviluppatori — Giochi protetti Wild-U

Questa sezione è pensata per essere copiata e mandata agli sviluppatori/tecnici. Spiega il contratto minimo per creare giochi compatibili con il launcher protetto Wild-U. 

OBIETTIVO
Ogni gioco Wild-U pubblicato su GitHub Pages deve funzionare solo se aperto dalla app madre/launcher.
Il launcher crea un ticket temporaneo Firestore e apre il gioco con ?launch=<ticketId>.
Il gioco, nel proprio index.html, deve validare quel ticket PRIMA di inizializzarsi.

ARCHITETTURA
1. La app madre legge game_versions.
2. Il launcher giochi mostra i giochi attivi.
3. Clic sul gioco → la app madre crea un documento in wildu_runtime_launches.
4. La app madre apre il gioco in iframe o redirect con ?launch=...
5. L'index del gioco carica /Wild-U/shared/wildu-secure-game-guard.js.
6. Il guard valida ticket/sessione.
7. Solo se OK vengono caricati gli script reali del gioco.
8. Se KO, viene mostrata schermata "Apri questo gioco dalla app Wild-U".

REQUISITI MINIMI DEL GIOCO
- Deve avere una cartella dedicata, es. /Wild-U/giochi/nome-gioco/
- Deve avere un index.html.
- Deve avere asset locali o same-origin quando possibile.
- Non deve inizializzare il gioco prima del guard.
- Se usa script classici, devono essere caricabili in ordine.
- Deve esporre preferibilmente window.init() oppure window.WilduGameStart().
- Non deve dipendere da Firebase proprio, salvo casi concordati.
- Non deve creare ticket: i ticket li crea solo la app madre.

COME DEVE ESSERE L'AVVIO
SBAGLIATO:
  <script src="js/main.js"></script>
  // il gioco parte anche da link diretto

CORRETTO:
  bootstrap guard
  → valida ticket/sessione
  → carica script del gioco
  → chiama init/start solo se autorizzato

SESSIONE LOCALE
Dopo il primo accesso valido, il guard crea una sessione locale del singolo gioco.
Così l'utente non viene disturbato a ogni refresh, ma il primo passaggio deve avvenire dalla app madre.

SICUREZZA REALISTICA
GitHub Pages serve HTML/JS/CSS pubblici. Non si impedisce il download del codice.
La protezione serve a impedire il funzionamento normale del gioco se aperto direttamente.

Snippet manuale base, se il tool non è usabile

<script type="module">
(async function () {
  const SCRIPT_URLS = [
    "js/state.js",
    "js/logic.js",
    "js/render.js",
    "js/ui.js",
    "js/input.js",
    "js/main.js"
  ];

  const { guardWilduGame } = await import("../../shared/wildu-secure-game-guard.js");

  try {
    await guardWilduGame({
      allowedKind: "secure_iframe",
      sessionMs: 11 * 60 * 60 * 1000,
      blockTitle: document.title || "Gioco protetto"
    });
  } catch (e) {
    return;
  }

  if (document.readyState === "loading") {
    await new Promise(resolve => document.addEventListener("DOMContentLoaded", resolve, { once: true }));
  }

  for (const src of SCRIPT_URLS) {
    await new Promise((resolve, reject) => {
      const s = document.createElement("script");
      s.src = src;
      s.onload = resolve;
      s.onerror = () => reject(new Error("Errore caricamento script: " + src));
      document.body.appendChild(s);
    });
  }

  if (typeof window.WilduGameStart === "function") window.WilduGameStart();
  else if (typeof window.init === "function") window.init();
})();
</script>

Cosa NON fare assolutamente

Non avviare il gioco prima del guard

  • Non lasciare <script src="js/main.js"> libero se quello script avvia il gioco.
  • Non mettere il guard dopo l’inizializzazione del gioco.
  • Non fare affidamento solo sul record Firestore game_versions: il file statico deve essere protetto.

Non hardcodare liste di giochi nel guard

  • Il guard deve dedurre il gioco corrente dal path o dal ticket.
  • Il tecnico deve gestire il link reale nel pannello admin, non dentro il sorgente del guard.

Non mischiare logica e protezione

  • Il guard decide solo se il gioco può partire.
  • La logica di gameplay deve restare nei file del gioco.
  • Non mettere funzioni di gioco dentro il guard shared.

Non creare fetch inutili

  • Il gioco non deve interrogare Firestore continuamente.
  • Il ticket si verifica una volta, poi sessione locale.
  • Leaderboards, analytics o cloud save vanno progettati separatamente.

Non rompere percorsi relativi

  • Se sposti l’index in un’altra cartella, rigenera il guard path.
  • Controlla CSS, immagini, audio e script relativi.
  • Il tool non riscrive asset URL: mantiene il markup originale.

Non usare il gioco 404

  • Un gioco non reale, come giochi/rifugio/ se oggi è 404, non va attivato.
  • Prima carica pagina reale, poi record in game_versions, poi test.

Se il tool non funziona o il gioco non è idoneo

  1. Gioco con build moderna/bundler: inserire il guard nel file entrypoint, prima di startGame().
  2. Gioco con script module: usare import diretto del guard e avviare solo dopo await guardWilduGame().
  3. Gioco con inline script enormi: spostare l’avvio in una funzione window.WilduGameStart.
  4. Gioco che parte subito appena carica una libreria: serve intervento manuale, perché il tool non può sapere dove fermare l’avvio.
  5. Gioco con iframe interni o CDN esterni: verificare che non partano contenuti esterni prima del guard.

Contratto minimo consigliato per nuovi giochi

// Nel gioco:
window.WilduGameStart = function () {
  // qui parte davvero il gioco
};

// Nell'index protetto:
await guardWilduGame();
await loadGameScripts();
window.WilduGameStart();

Test obbligatori

  • Apri il link diretto senza ?launch: deve bloccare.
  • Apri dal launcher: deve partire.
  • Controlla iframe URL: deve contenere ?launch=....
  • Refresh entro 11 ore: deve rientrare grazie alla sessione locale.
  • Disattiva gioco in admin: non deve più comparire nel launcher.
  • Aumenta rev: il launcher/SW deve vedere la nuova versione secondo la cache strategy attuale.
